# 标准开发流程

## 原则

- 文档用于消除歧义，不替代可运行代码和验证结果。
- 人类负责目标、取舍与发布许可；Agent 负责分析、实现、验证和记录。
- 一次只交付一个可独立验证、可独立回滚的增量。
- 需求、设计、代码、测试和发布记录相互引用，形成可追踪链路。
- 代码和按序执行后的数据库迁移是当前事实；文档冲突时同步修正文档。

## 标准路径

1. 项目声明：确认产品边界、技术栈、架构、目录和命名规范。
2. 需求探索：区分已确认事实、假设、问题、风险和建议。
3. BRD/PRD：定义用户、场景、目标、非目标、业务规则和成功指标。
4. UI 说明：覆盖正常、加载、空、错误、离线、权限不足和完成状态。
5. 技术设计：说明数据流、权限、缓存、迁移、性能、安全和降级策略。
6. 开发计划：拆成多个可验证增量，列明文件边界、验收和回滚。
7. 实现：严格按当前增量执行，出现越界需求时暂停扩张并重新确认。
8. 测试：逻辑、接口和真实浏览器流程分别验证。
9. 发布：先确认环境、配置、迁移、监控与回滚点，再取得发布许可。
10. 归档：稳定结论回写 `docs/project/`，任务文件移入 `docs/work/archive/`。

## 四个交付闸门

### 闸门一：需求准备完成（Definition of Ready）

开始计划前必须满足：

- 用户与使用场景明确。
- 目标、非目标和成功标准明确。
- 核心业务规则与边界已回答。
- 假设被明确标记，没有伪装成事实。
- 验收标准能够通过观察或测试判定。
- 权限、隐私、费用和不可逆操作已经识别。

未满足时允许继续探索或制作原型，不进入完整开发。

### 闸门二：影响范围确认

编码前必须列出：

- 本轮新增和修改的文件。
- 明确不修改的页面、模块、数据表和交互。
- 是否需要数据库迁移、环境变量或外部服务。
- 对登录、离线、性能、现有数据和部署的影响。
- 风险等级与审查方式。

实施中如需越界，先更新任务文档；若会改变用户意图、数据库或外部状态，取得用户确认。

### 闸门三：可验证增量

每个增量必须：

- 只包含一个可说明的结果。
- 构建或类型检查通过。
- 有对应验收步骤。
- 不依赖尚未完成的大批后续代码才能运行。
- 能通过提交、开关或兼容实现单独回滚。

### 闸门四：发布许可

发布前必须确认：

- 目标环境与公开范围。
- 环境变量和密钥归属正确。
- 数据库迁移向后兼容且有恢复策略。
- 核心页面与接口测试完成。
- 已记录可回滚的代码提交和部署版本。
- 用户已授权本次外部发布。

## Definition of Done

任务仅在以下条件全部满足时完成：

- 功能与非目标边界一致。
- 所有验收标准有结果记录。
- 类型/构建检查通过。
- 涉及交互时完成真实页面点击验证。
- 涉及 API 时验证成功、未登录、无效输入和重复请求。
- 涉及迁移时验证 RLS、旧数据兼容和向前修复路径。
- 没有提交密钥、生成目录或无关改动。
- 稳定结论已经同步，任务文档已经归档。
- 已记录提交、部署地址、部署版本和回滚方式（如适用）。

## 独立审查

以下变更必须进行独立反方审查：

- 登录、权限、支付、密钥和个人数据。
- 不可逆数据库迁移或大量数据处理。
- 跨模块重构、技术栈变更。
- 面向真实用户的正式生产发布。

审查者重点寻找遗漏的边界、错误假设、安全风险和不可行回滚。可使用不同模型时，由一个模型提出方案、另一个模型扮演反方；最终取舍由人类确认。没有第二模型时，必须另起一次不依赖原结论的反方检查并记录局限。

## 追踪方式

每个重要功能分配稳定 ID，例如 `FEAT-004`，并在任务文档中引用相关 PRD、UI、技术设计、测试记录、提交和部署版本。反向文档至少引用该任务 ID，避免复制同一段内容。
